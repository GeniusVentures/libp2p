<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Integrator DI graph -> ConnectionGater instance | Whatever concrete class an integrator binds via useConnectionGater<>() runs with full authority to accept/reject every connection stage; a buggy/malicious custom gater is outside this phase's control surface |
| Default (unconfigured) host -> PermissiveConnectionGater | GATE-02 mandates fully-permissive default behavior — a deliberate secure-by-default deviation, not an oversight |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-------------------|
| T-01-01 | Elevation of Privilege | Default PermissiveConnectionGater binding | medium | accept | GATE-02 explicitly requires default-permissive behavior so existing hosts are unaffected; documented here as a deliberate, requirements-locked deviation from secure-by-default, not a silent gap. Reference deny-by-default policy (POLICY-01) is deferred to v2 by REQUIREMENTS.md. |
| T-01-02 | Tampering | ConnectionGaterError category / message text | low | accept | Error messages only ever describe which internal hook rejected a connection; no attacker-controlled data is echoed into the message strings (all 5 messages are static literals), so no injection surface. |
| T-01-03 | Repudiation | Silent gater misconfiguration (integrator forgets to bind a custom gater) | low | mitigate | useConnectionGater<>() follows the exact same discoverable pattern (Doxygen example + injector helper) as useSecurityAdaptors<>()/useTransportAdaptors<>(), minimizing the chance an integrator misses the override point. |
</threat_model>
